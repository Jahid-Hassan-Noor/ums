University Management System

Project documentation grounded in the current repository

A functional, architectural, data, API, security, deployment, and quality overview of the university management system as implemented in the Django and Next.js codebase.

Source review updated 21 October 2026
University

The project consolidates the configurable public university website, applicant admissions, student self-service, teaching and learning workflows, executive academic governance, administrative operations, and specialist service desks into one role-based UMS. The backend is a modular Django REST application; the frontend is a Next.js App Router application with separate route zones for each role and a public website.

2. Users and system requirements

Access is based on a single Profile.role value with a corresponding role-detail record. The supported roles are applicant, student, teacher, executive, librarian, caterer, technician, accountant, HR, and admin.

Applicant

Registers through the applicant flow, manages one or more intake applications, uploads evidence, adds scholarship information, submits, and tracks staff decisions.

Student

Uses courses, registration, assignments, attendance, timetable, results, exam slips, leave, elections, library, venue booking, emergency contacts, canteen visibility, and ICT support.

Teacher

Manages assigned courses, resources, assignments, submissions, attendance sessions and corrections, a searchable course roster with attendance summaries and CSV export, result drafts, leave decisions, timetables, and venue requests.

Executive

Operates within school, centre, department, programme, or unit scope; manages offerings, schedules, final exams, people, results, reports, and organization data.

Librarian

Maintains books, copies, shelves, laptops, borrow requests, loans, returns, and student circulation records.

Caterer

Searches eligible students, views the active monthly meal account, and records canteen deductions without the ability to add credit.

Technician

Receives student ICT helpdesk tickets, manages assignment and status, posts progress notes, and records resolution details.

Accountant

Manages finance gateway settings, subscription plans, payment status, subscription records, student ledgers, posted charges, balances, finance holds, per-student PDF/XLSX ledger exports, and finance-side notifications.

Human Resources

Maintains the university employee master, HR staff accounts, positions, employment status, reporting relationships, applicant and employee onboarding boards, and self-service HR profile access.

Administrator

Owns cross-system configuration: people, academic directory, semesters, settings, venues, hostels, canteen policy, content, reports, elections, audits, and operational governance.

2.1 Functional and non-functional requirements

Core functional requirements

  • Authenticate a user and route them to the correct role zone.
  • Enforce role and executive-scope authorization on every protected API.
  • Maintain one shared academic directory for public and authenticated experiences.
  • Support applicant, academic, learning, result, student-life, finance, and campus-service workflows.
  • Notify affected users and retain auditable administrative changes.
  • Produce downloadable operational and academic reports.

Quality requirements reflected in code

  • Strict TypeScript compilation on the frontend.
  • Serializer and service-layer validation on backend writes.
  • PostgreSQL relational constraints and transactional operations.
  • Container health checks and database readiness handling.
  • Centralized image-upload validation for extension, content type, magic bytes, file size, and decompression-bomb checks.
  • Pagination, scoped querysets, and targeted query optimization.
  • Background execution for due reminders and monthly canteen allowance initialization.

3. Architecture and design

The ums uses a decoupled client/server design with a shared reverse proxy. The frontend renders public and protected pages; the backend owns identity, authorization, validation, business rules, persistence, files, reporting, and notifications.

3.1 Request and data flow

  • Public pages: Next.js server/client code reads public APIs from home_app.
  • Browser API calls: the frontend uses NEXT_PUBLIC_API_URL, defaulting to /api.
  • Nginx: requests under /api/ are forwarded to Django after the /api prefix is removed.
  • Direct Next.js development: Next.js rewrites /api/* to the configured proxy target.
  • Protected calls: the client adds Authorization: Bearer <access-token>.
  • Backend: DRF authentication, role permissions, ums policy middleware, domain services, and serializers validate the request before ORM persistence.

4.1 Frontend role experiences

The frontend contains dedicated route groups and navigation definitions for all ten roles. Some pages have purpose-built feature components; others are rendered through shared createRoleZonePage or schedule factories. Twenty-five page routes currently use shared role-zone/schedule page construction: 17 role-zone pages and eight student/teacher schedule pages. A shared component alone does not indicate an unfinished workflow.

Purpose-built operational screens

Admissions, people management, academic directory, semesters, settings, reports, public content, venues, venue booking, canteen, library acquisition/circulation, helpdesk, elections, courses, leave, academic calendars, HR onboarding, teacher rosters, finance ledger exports, and student results.

Shared data-driven screens

Student and teacher calendars and timetables fetch role-specific events. They show loading, empty, and request-error states; an API failure no longer displays built-in sample events. Several dashboards intentionally provide navigation to operational pages.

Unimplemented staff leave tracking

HR employee records have no staff leave policy, accrual, request, approval, or balance ledger. The API retains nullable leave fields with is_placeholder and the UI says "Not configured". Teacher course details, assignment details, submission review, and the searchable roster are working API-backed screens.

6. Key end-to-end workflows

6.1 Authentication, session refresh, and authorization

  1. A user submits username and password to the Next.js /ums-auth/session route, which forwards only approved login/register endpoints to Django.
  2. Django authenticates the account, rejects inactive profiles, and returns access/refresh JWTs plus serialized user/role data.
  3. The Next.js session route stores JWTs, role, and executive-scope state in HttpOnly SameSite cookies. Browser JavaScript receives only the sanitized session/user payload.
  4. The Next.js proxy and /ums-auth/backend/... route handlers refresh expired access tokens while the rotating refresh token remains valid.
  5. Client API calls go through /ums-auth/backend; the route handler attaches the Bearer token server-side before forwarding to Django.
  6. DRF role permission classes enforce the real security boundary; frontend redirects are navigation assistance, not authorization.

This is a unified portal login, not external identity-provider SSO. The Next.js session layer uses HttpOnly SameSite cookies and refresh token rotation. Production review should cover CSRF, revocation, and session/device management.

Account recovery sends a reset link when email delivery is configured. Public self-registration at the root auth endpoint is disabled for ordinary roles; admins create staff/student accounts, while applicants use the separate applicant registration flow. Email-verification endpoints currently report that verification is not required for ums accounts.

6.3 Course content, assignments, and attendance

Learning workflow

  • Teacher organizes content into sections and folders.
  • Resources support uploaded files or URLs with publication windows.
  • Assignments and lab activities enforce opening/due dates, allowed file formats, per-file size and file-count limits, late-submission policy, attempt rules, and optional rubrics.
  • Group projects support teacher-defined capacity and membership criteria, leader-created groups, invitations, one group per student, and leader-only final submissions.
  • Course announcements support individual or group presentation slots with a teacher-defined capacity; a group leader selects the group slot while individual presentations remain supported.
  • Students submit content and attachments; teachers review and return feedback. Announcements and assignment events can notify enrolled students.
  • Teachers can search the enrolled course roster, review tutorial and lab groups plus attendance summaries, and export the visible rows as CSV. The roster API checks that the offering belongs to the requesting teacher.

Attendance workflow

  • Teacher opens a session linked to an offering and optionally a class meeting.
  • The session has code/QR credentials, opening/closing times, and status.
  • Student check-in validates enrollment, session state, code/token, and duplicates.
  • Teachers can record late/manual statuses and corrections.
  • Low-attendance warnings are generated after enough class history exists.

6.4 Results, final exams, and publication

Teachers enter marks against the active enrollment roster, save partial work as a draft, and submit a complete result batch for review. Executives can inspect every record within their assigned academic scope, return a batch with a correction note, approve it, and publish it. Publication creates or updates student transcript records, recalculates semester GPA and cumulative CGPA, and notifies the affected students and teacher. Student-facing semester, completed, coursework, GPA, transcript, and exam-slip APIs/pages expose the published academic record. 

Teacher records or submits marks
    → Executive reviews scoped result data
        → Result batch is approved/published
            → Student-facing result and transcript views expose published data

Final exams are scheduled by executives against course offerings. The scheduling service checks:

  • semester exam windows and schedule lock dates;
  • students enrolled in overlapping examinations;
  • venue capacity across one or more allocated venues;
  • conflicts with approved venue bookings and recurring classes;
  • duplicate final examinations for the same offering.

Student exam slips and semester-result PDFs are generated with ReportLab. Final exam data is also merged into student timetable responses.

6.5 Student services and operational workflows

Leave approval

A leave request creates approval rows for relevant teachers and a dean. Notifications are issued, decisions are tracked, and the request reaches approval only after the required decisions complete.

Venue booking

Students or teachers request a venue; submission checks schedule conflicts. Admin decisions re-check availability and notify the requester. Rejection requires a reason.

Library circulation

Students request an available book or laptop, or request that a new title be acquired. Librarians review requests, assign a physical asset, create a loan, and record return/condition data.

Canteen allowance

Eligible active students receive the configured monthly allowance. Caterers can deduct purchases; admins manage bonuses and justified adjustments.

ICT helpdesk

Students open tickets and see status history. Technicians triage, assign, update, and resolve them with notes visible to the student.

Elections

Technicians configure election type, timing, seats, and candidates. Eligibility and exact ballot counts are enforced; result snapshots can be published to eligible students.

HR onboarding

HR staff manage applicant and onboarding columns, create cards, move them with recorded history and optional reasons, and link a card to one employee record after it enters onboarding. Stale moves and duplicate employee links are rejected.

Student ledger export

Accountants review a student's charges and posted ledger entries, then download that student's ledger as PDF or XLSX. The export API validates the format and student role.

9. Security, policy, and reliability

Authorization layers

  • Next.js proxy redirects users away from another role's route zone.
  • DRF HasProfileRole subclasses enforce backend role access.
  • Executive queries and mutations apply academic scope filters.
  • Object-level services verify ownership, enrollment, assignment, or eligibility.

Operational policy middleware

  • Maintenance mode can disable normal ums traffic.
  • Read-only mode blocks state-changing methods.
  • Individual ums modules can be disabled through settings.
  • Settings and audit endpoints remain available for recovery/control.

Validation and data safety

  • Django password validators and hashed password storage.
  • Serializer/service validation for roles, scopes, dates, capacities, conflicts, and statuses.
  • Upload constraints for profile images, resources, assignment files, and documents.
  • Database transactions and row locks in conflict-sensitive workflows.

Audit and notifications

  • Administrative and executive mutations are captured by audit middleware.
  • Sensitive request values are redacted before audit persistence.
  • Notifications carry an event type and optional deep link.
  • Role fan-out excludes inactive profiles and supports actor exclusion.

Security follow-up: the role cookie is now set HttpOnly by the Next.js session/proxy layer, but it is still only a routing hint. It must never be treated as proof of authorization. The backend permission and object-scope checks are the authoritative controls.

14. Security hardening roadmap

Backend role checks and object-scope rules are meaningful strengths, but production hardening should focus on private files, deployment defaults, endpoint-specific abuse resistance, dependency patching, gateway/webhook operations, and recovery. Session handling and upload validation have improved materially in the current worktree, but still need production review.

Priority Observed condition Required improvement
P1 Nginx proxies /media/ to Django's protected media view and uses an internal location for authorized files. Public settings images have a separate direct route. The authorization map still needs coverage review as file types grow. Test access to each private file type across roles and owners, verify the internal redirect is unreachable externally, and keep new upload types on the protected-media path.
P0 The August dependency-audit counts are stale after package changes; this revision did not run a fresh audit. Run npm audit --omit=dev in the frontend container, triage current findings, and review packages with incompatible peer dependency ranges before release.

Measure before changing

  • Add request latency, database query count/time, task duration, queue depth, cache hit ratio, and frontend Web Vitals.
  • Establish budgets for dashboard, list, report, upload, and schedule endpoints.
  • Add query-count tests to the highest-traffic APIs before refactoring them.

Database and API

  • Standardize pagination for manual APIView responses; the codebase has 250+ APIView classes and 700+ manual Response constructions.
  • Profile common filters and add composite/partial indexes only from measured query plans; just three explicit models.Index declarations exist today.
  • Continue select_related/prefetch_related use and add tests that prevent N+1 regressions in serializers and list payloads.

Redis and background work

  • Configure Django's shared Redis cache rather than relying on the process-local default cache for settings and reminder throttles.
  • Cache stable public directory/CMS payloads and expensive dashboard aggregates with explicit invalidation.
  • Move large reports, email delivery, image/document processing, imports, and high-volume notification fan-out to Celery.

Frontend delivery

  • Keep data fetching server-side where interaction is unnecessary; review client component boundaries before adding more browser bundles.
  • Split heavy role workspaces by tab/dialog, dynamically load scheduler/chart/export tools, and virtualize long lists.
  • Replace repeated mount-time fetch effects with a consistent query layer that supports cancellation, deduplication, caching, and invalidation.

Redis and Django's Redis cache backend are configured. Measure cache hit rates, identify endpoints that benefit from caching, and define invalidation rules before expanding cache use. See the Django cache framework.
